CostGuard — the recommendation ledger

Status: draft Date: 2026-09-06 Surface: /costguard Sources: src/components/sidebar/Sidebar.tsx · src/components/home/KpiCard.tsx · src/components/home/RecommendationsCard.tsx · workshop-data/seed.sql · DESIGN_CONTEXT.md · docs.finout.io/user-guide/optimize/costguard · finout.io/blog/the-savings-that-never-show-up

1. Problem

Finding cloud waste is solved. Every cloud already emits recommendations, and Finout already unifies, prioritises and assigns them. What is not solved is everything after the list: nobody can prove the money was ever saved. Finout's own writing names the failure modes — "a recommendation without a named individual owner defaults to no one", decisions made in Slack with no audit trail, and tickets closed without checking whether the projected saving reached the bill.

Our own data contains the sharpest version of this. Snowflake Warehouse weekend cost ran at 40% of weekday ($155 vs $383/day) from April through 5 June — an optimisation that was working. On 6 June it stopped: weekends now cost 100% of weekday ($390 vs $389). That regression has cost $5,596 across 24 weekend days, ≈$2,075/month, and it is still running today. No anomaly fired: all five rows in the anomalies table are other services.

So the problem is not only that savings are unproven. A saving that was real can quietly die, and today nothing is watching.

Meanwhile the product advertises the destination in three places and delivers a toast.

2. Who it's for

Primary — the FinOps lead. Owns the total number and has to answer "what did the programme actually save this quarter?" Today they cannot, because implementation lives in other people's backlogs.

Secondary — the engineering owner. Receives the work. Needs to know it is genuinely theirs, how much it is worth, and that closing it will be believed. Allergic to being handed someone else's cleanup.

Secondary — the executive. Wants one number, its trend, and evidence somebody is acting. Reads the top of the screen and leaves.

Not served in this version: anyone doing the remediation itself. This screen tracks work; it does not perform it.

3. What exists today

  • Sidebar.tsx lists CostGuard under Optimize. It has no href. One of twelve dead nav items out of sixteen.
  • KpiCard.tsx shows "Monthly potential savings · $26,802" with a "Go to CostGuard" button whose handler is showToast("CostGuard is next in the workshop 😉").
  • RecommendationsCard.tsx lists RDS - Idle, RDS - Rightsizing, K8s - Deployment with per-row savings, a Cost Waste Percentage, and a Number of Resources column. Its action fires showToast("Opening scan in CostGuard…").
  • /anomalies exists and is a genuinely different job: it detects unexpected change. This screen tracks committed work. They should link, not merge.

The status quo we are competing with is a spreadsheet of optimisation tickets pasted into a monthly Slack update. It is honestly adequate for tracking that work happened. It cannot verify the bill went down, and it cannot notice a saving reverting. That is the only ground on which this screen wins.

4. Non-goals

  • The scan engine. Recommendations are assumed to arrive. We do not detect them here.
  • Cloud-native scan ingestion (AWS Compute Optimizer, Azure Advisor, GCP Recommender).
  • Jira sync. Finout marks it "coming soon"; we design the owner and status model it would need, and stop there.
  • Commitments and Savings Plans. Separate nav items, separate purchase workflow.
  • Resource-level drill-down. See Decision D1.
  • Performing remediation. No infrastructure is changed from this screen.

5. Decisions

DecisionChoiceWhy
D1 Unit of the screenThe recommendation, not the resourcecost_events is grained at service × team × environment × day and has no resource identity. A recommendation references a service, which the data supports. Home's Number of Resources column stays on Home and is out of scope here — noted, not silently dropped
D2 What "Act" meansAssign a named owner and a due date inside FinoutJira sync is a non-goal, but the ownership model it needs is exactly what fixes "defaults to no one". Design the model, not the integration
D3 What "realized" meansActual service cost over the 14 days after done_at, compared against the 14 days before created_at, expressed as $/monthIt is computable from cost_events today, and 14 days matches CostGuard's documented analysis window
D4 What happens after DoneVerification keeps running. If cost returns to baseline, status becomes RegressedThis is the gap. Finout's "Prove" is described as a report; our data proves it has to be a watchdog
D5 Status modelReal four — New · Working on it · Done · Dismissed — plus derived RegressedMatches the shipped product so it stays recognisable; the fifth state is the new idea and is derived, never set by hand
D6 Verification without a baselineShow "Not verifiable", never $0A missing baseline is not a zero saving. Claiming otherwise is the exact dishonesty this screen exists to end
D7 DismissedKept, filterable, and re-raised if the same opportunity recurs after 90 daysFinout's post names opportunities that "resurface repeatedly" — silent deletion is how that happens

6. User stories

  1. As a FinOps lead, I want every open recommendation to show a named owner and an age, so I can see what is stalled without opening a spreadsheet.
  2. As a FinOps lead, I want projected savings and realized savings side by side, so I can report what actually reached the bill.
  3. As a FinOps lead, I want to be told when a saving I already banked has come back, so I stop counting money I no longer save.
  4. As an engineering owner, I want to see why this was assigned to me and what it is worth, so I can judge it against my other work.
  5. As an engineering owner, I want to move an item to Working on it and Done and have the system check my work, so closing it means something.
  6. As an executive, I want one realized-savings number with a trend, so I can tell whether the programme is working.
  7. As a FinOps lead, I want to dismiss a recommendation with a reason and have it come back if it recurs, so the same argument is not had twice.

The fourth row is the one that justifies the screen: the gap between what is being lost and what is being noticed is presently the whole amount.

8. Open questions

  • Who assigns owners — auto-assign from the team on cost_events, or always a human choice? Auto-assignment is what Finout advertises via Virtual Tags, but wrong auto-assignment is how engineers learn to ignore a tool. Decide with Daniel before build.
  • How long must a saving hold before it counts as realized — 14 days, or a full billing cycle? Affects only copy and thresholds, not layout.
  • Should Regressed reopen the original item or create a new one? Reopening keeps the history together; a new item keeps the realization stats honest. Leaning reopen with a visible event log. Designer's input welcome.
  • Does the executive need a separate view, or is the top of this screen enough?

Appendix — how the numbers were derived

Computed from workshop-data/seed.sql, all 12,172 cost_events rows parsed.

Snowflake Warehouse (service 17)

  • Baseline 1 Apr – 5 Jun: weekday $383/day, weekend $155/day = 40%
  • Since 6 Jun: weekday $389/day, weekend $390/day = 100%
  • Expected weekend at baseline ratio: $157/day → excess $233/weekend-day
  • 24 weekend days → $5,596 total ≈ $2,075/month

EKS Cluster (service 1) — the second undetected story

  • 1–14 Apr: $32,398 over 668,792 vCPU-hours = $0.0484/vCPU-h
  • 13–26 Aug: $37,898 over 698,503 vCPU-hours = $0.0543/vCPU-h
  • Unit cost +12.2% while usage rose 4.4% → ≈$8,950/month of drift

Two discrepancies with workshop-data/README.md, flagged not resolved:

  1. The README states the Snowflake gap is ~$1,412/mo; computing from the rows gives $2,075/mo. Different baseline method, most likely. The computed figure is used here because it is reproducible from the data.
  2. The README describes three flagged anomalies. The anomalies table contains five: Anthropic API, BigQuery, Datadog Logs, EC2 Instances and S3 Storage. The last two are not mentioned in the README. Only three carry a cost_impact_usd.

Neither affects the design. Both should be reconciled before the workshop, since participants will compute these themselves.
